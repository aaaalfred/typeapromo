# Buckets R2 y política CORS

El pipeline de imágenes usa **dos buckets** con propósitos opuestos. Confundirlos es el error que
convierte un almacén de imágenes en un almacén de malware servido desde tu dominio, así que la
separación no es negociable.

| Bucket | Variable | Acceso | Contenido |
|--------|----------|--------|-----------|
| `forms-media-staging` | `R2_BUCKET_STAGING` | **Privado**, sin dominio público | Cargas temporales sin validar |
| `forms-media-public` | `R2_BUCKET_PUBLIC` | Lectura pública por dominio propio | WebP ya procesados, sin EXIF |

Lo que llega del navegador aterriza siempre en el privado. Solo tras verificar la firma binaria,
el tamaño y las dimensiones, y tras reprocesar con Sharp, el resultado se copia al público. El
original nunca se sirve.

## 1. Crear los buckets

En el panel de Cloudflare, **R2 → Create bucket**, dos veces:

```
forms-media-staging
forms-media-public
```

O con Wrangler:

```bash
npx wrangler r2 bucket create forms-media-staging
npx wrangler r2 bucket create forms-media-public
```

Los nombres son libres: lo que manda son las variables de entorno. Los de aquí son los que usa el
compose local con MinIO, y mantenerlos iguales evita sorpresas.

## 2. Exponer solo el bucket público

En `forms-media-public` → **Settings → Public access**, conecta un **dominio propio** (por
ejemplo `media.tu-dominio.com`). Esa URL es la que va en `MEDIA_PUBLIC_BASE_URL`.

```
MEDIA_PUBLIC_BASE_URL=https://media.tu-dominio.com
```

Dos matices que ahorran una tarde de depuración:

- El subdominio `*.r2.dev` de desarrollo **no sirve**: tiene límite de peticiones y Cloudflare
  documenta expresamente que no es para producción.
- `forms-media-staging` se queda **sin acceso público de ningún tipo**. Si tiene dominio
  conectado, alguien puede leer bytes sin validar directamente desde tu dominio.

Las claves del bucket público son impredecibles (`media/<uuid>/<hash>/…`) e inmutables — cambiar
la imagen cambia el hash y por tanto la clave —, así que se pueden servir con caché agresiva:

```
Cache-Control: public, max-age=31536000, immutable
```

## 3. CORS del bucket de staging

Esta es la pieza que quedó pendiente en la fase 6 y sin la cual **la subida desde el navegador
falla siempre**, con un error de CORS que no dice nada útil.

El navegador sube directamente al endpoint S3 de R2 con la URL prefirmada que devuelve
`POST /api/media/upload-intent`. Eso es una petición **entre orígenes**: de
`https://formularios.tu-dominio.com` a `https://<account-id>.r2.cloudflarestorage.com`. Sin
política CORS, el preflight `OPTIONS` no pasa.

En `forms-media-staging` → **Settings → CORS Policy → Add CORS policy**:

```json
[
  {
    "AllowedOrigins": [
      "https://formularios.tu-dominio.com"
    ],
    "AllowedMethods": ["PUT", "HEAD"],
    "AllowedHeaders": ["content-type", "content-length"],
    "ExposeHeaders": ["etag"],
    "MaxAgeSeconds": 3600
  }
]
```

Punto por punto, y por qué:

- **`AllowedMethods: ["PUT", "HEAD"]`** y nada más, tal y como fija `PR.md`. `PUT` es la subida;
  `HEAD` permite comprobar el objeto sin descargarlo. **No** se añade `GET`: nadie debe leer
  staging desde el navegador. **No** se añade `DELETE`: el borrado lo hace el servidor con sus
  credenciales, jamás el cliente.
- **`AllowedOrigins`** es la lista literal de orígenes de la aplicación, uno por entorno. Nunca
  `"*"`: con comodín, cualquier página de internet podría usar una URL prefirmada filtrada.
  Incluye el esquema y, si no es el estándar, el puerto.
- **`AllowedHeaders`** debe incluir `content-type` y `content-length` porque van **firmados** en
  la URL prefirmada: si el navegador no los puede enviar, el `PUT` se rechaza por firma inválida.
- `OPTIONS` no se declara: R2 responde al preflight a partir de esta misma política.

Con Wrangler:

```bash
npx wrangler r2 bucket cors put forms-media-staging --file cors-staging.json
npx wrangler r2 bucket cors list forms-media-staging   # comprobar
```

### ¿Y el bucket público?

No necesita CORS para mostrar imágenes: un `<img src>` no es una petición CORS. Solo hace falta
si alguna vez se leen esos bytes con `fetch()` desde el navegador, cosa que esta aplicación no
hace.

## 4. Credenciales de API

**R2 → Manage R2 API Tokens → Create API token**, con permiso *Object Read & Write* limitado a
los dos buckets. De ahí salen tres valores:

```
R2_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
R2_ACCESS_KEY_ID=…
R2_SECRET_ACCESS_KEY=…
```

Ninguna lleva prefijo `NEXT_PUBLIC_`, así que **solo existen en el servidor**;
`src/lib/storage/entorno.ts` se niega a ejecutarse si detecta un `window`, de modo que un import
accidental desde el cliente falla ruidosamente en vez de degradar en silencio.

`S3_FORCE_PATH_STYLE` debe estar **ausente o a `0`** con R2 (el bucket va en el host) y a `1` con
MinIO en local (exige `endpoint/bucket/clave`).

## 5. Configuración completa

```bash
R2_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
R2_ACCESS_KEY_ID=…
R2_SECRET_ACCESS_KEY=…
R2_BUCKET_STAGING=forms-media-staging
R2_BUCKET_PUBLIC=forms-media-public
MEDIA_PUBLIC_BASE_URL=https://media.tu-dominio.com
# S3_FORCE_PATH_STYLE ausente con R2
```

## 6. Comprobar que funciona

Desde el editor, sube una imagen a un formulario. Recorrido esperado:

1. `POST /api/media/upload-intent` → `201` con una URL `PUT` firmada contra el bucket privado.
2. El navegador hace el `PUT` directo a R2 → `200`. **Si aquí hay error de CORS, revisa el paso 3.**
3. `POST /api/media/:id/complete` → verificación, Sharp, publicación.
4. La imagen se ve en el editor con una URL de `MEDIA_PUBLIC_BASE_URL`.
5. En `forms-media-staging` no queda nada: el objeto temporal se borra al promocionar.

Prueba manual del preflight:

```bash
curl -i -X OPTIONS "https://<account-id>.r2.cloudflarestorage.com/forms-media-staging/prueba" \
  -H "Origin: https://formularios.tu-dominio.com" \
  -H "Access-Control-Request-Method: PUT" \
  -H "Access-Control-Request-Headers: content-type"
# Debe responder 200 con access-control-allow-origin y access-control-allow-methods: PUT, HEAD
```

## 7. MinIO no es R2

`PLAN.md` §2.10 lo deja escrito y conviene repetirlo: MinIO valida el **flujo**, no la
**compatibilidad**. El presign y el CORS de R2 hay que probarlos contra R2 real al menos una vez
antes de dar por buena la fase de media. Los dos sitios donde divergen en la práctica son
`forcePathStyle` y qué cabeceras acepta el preflight.

## 8. Limpieza

Ni las cargas incompletas de staging ni los activos publicados que dejan de usarse desaparecen
solos: los borra el cron descrito en
[Despliegue y operación → Cron de limpieza](./despliegue.md#cron-de-limpieza). Sin ese cron, el
bucket privado crece indefinidamente con subidas a medias.
